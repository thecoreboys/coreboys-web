# Community inbox

“Help & suggestions” opens a short dialog with a sliding **Sign up to help / Suggest something** control. The corner utility is desktop-only; phones and tablets use the header menu. The form code loads on demand. The dialog is hidden in Admin, Studio, and the preview-access screen.

Help signups ask for a name, one email or contact handle, a role, and a short message. A portfolio link is optional. Suggestions require only a message; contact details are optional. Help signups require a custom checkmark confirming “I am 18 years of age or older.” Suggestions have no age checkbox or attestation requirement; new suggestions store age_confirmed=false. The role field uses the shared custom dropdown. Older applications remain readable. Drafts stay separate when switching forms and remain available after a failed request. The marketing introduction has been removed, and success shows a short confirmation.

Admins use **Community inbox** at `/admin/contributors`, linked from the admin dashboard. Type filters separate help signups and suggestions; status filters show new or reviewed entries. Counts cover the whole inbox, and filtered results paginate 25 at a time. Each entry supports copying contact details and marking it reviewed or new. Older applications remain visible with all original contact fields. The page and data API require the live admin role; member managers cannot read or update submissions.

Details are encrypted with AES-256-GCM using purpose-separated keys derived from `CONTRIBUTOR_SECRET`, falling back to `FAN_SESSION_SECRET`. Keep the chosen secret stable and backed up; changing it without migrating the ciphertext makes stored submissions unreadable. Type and review status are separate metadata columns so filtering happens before pagination. No public listing or external notification is added.

The public POST checks Origin, JSON content type, the actual streamed 16 KiB body limit, strict server validation, a honeypot, and an IP-bound signed 30-minute form token. Tokens cannot be submitted in their first two seconds, and token IDs are unique so retries do not duplicate entries. Shared limits allow ten attempts per 15 minutes and five saved submissions per visitor fingerprint per day. A transaction advisory lock serializes the daily limit across replicas; raw IP addresses are not stored. Submitted portfolio links must use HTTPS without credentials and are never fetched by the server. User text is rendered as React text.

Admin review updates require an authenticated admin, same-origin JSON, a bounded request, a valid UUID, and a status of `new` or `reviewed`. All inbox responses use `private, no-store`. Development alone allows equivalent loopback aliases on the same protocol and port when browser metadata says same-origin, matching Next’s local URL rewriting.

Migrations `065_contributor_applications.sql`, `069_community_inbox.sql`, and `073_community_age_confirmation.sql` are registered in the web migration runner. The additive schema is also initialized lazily on the first save or inbox request. Existing rows default to help signups with a new review status. Both the original payload shape and new form payloads remain accepted for clients that already have the old form open.

Validation covers both forms, legacy compatibility, encryption, token replay and limits, authorization, server filters and pagination, and review writes. UI checks use desktop and phone viewports; the admin preview uses fictional in-memory data without accessing private submissions. Screenshots are saved in the workspace’s `output/community-forms/` directory. The form keeps one scroll container within the visual viewport and restores keyboard focus when closed.
